1. Core Definition & Theoretical Framework

Systems Development Life Cycle (SDLC): The process of understanding how an information system can support business needs, designing and building the system, and delivering it to users.

資訊系統開發的目標不是為技術而技術；真正的核心是 Business Value，包括降低成本、提升服務品質、改善營運效率。Business Need → Requirements → Models → Design → Operational System。各階段產出物為下個階段提供輸入，形成 progressive refinement。

2. Four Fundamental SDLC Phases

Copyable Mermaid source
flowchart LR\n P["Planning: WHY"] --> A["Analysis: WHAT"]\n A --> D["Design: HOW"]\n D --> I["Implementation: BUILD / TEST / DEPLOY"]

Planning: Why build the system?

Project Initiation: Receive System Request or RFP; clarify the Business Problem, Goals and expected Business Value; perform Technical, Economic and Organizational Feasibility; obtain approval. Project Management: Develop Work Plan, Staff Project, Monitor and Control. Deliverables: System Request, Feasibility Analysis, Project Plan.

System Request typically contains Project Sponsor, Business Need, Business Requirements, Business Value, and Special Issues. RFP (Request for Proposal) solicits external vendor proposals; it is not identical to an internal System Request.

FeasibilityCentral QuestionKey Checks
Technical FeasibilityCan we build it?Technology familiarity, functional-area knowledge, project size, compatibility.
Economic FeasibilityShould we build it?Development/operating costs, annual benefits, tangible and intangible value.
Organizational FeasibilityWill they come?Strategic alignment, management support, champions, adoption.

Analysis: What should the system do?

Develop Analysis Strategy by investigating As-Is and To-Be operations. Gather and refine Requirements, specify WHO / WHAT / WHERE / WHEN, and create Functional, Structural and Behavioral Models. Deliverable: System Proposal, consolidating Requirements Definition, System Concept and models. Analysis emphasizes logical business requirements rather than selected server products or SQL implementation.

Design: How will the system work?

Four steps: (1) Design Strategy (Build, Buy, Outsource). (2) Architecture and Interface Design (Software, Hardware, Network; User Interface and Component Interface). (3) Database and File Specifications. (4) Program Design defining modules and inputs/outputs. Deliverable: System Specification.

Implementation: Build, test, install and support

System Construction (coding/testing), Installation and User Training, Support and Maintenance, and Configuration Management. Configuration Management includes identifying controlled configuration items, managing changes, and maintaining version/status records; Git alone is not the whole discipline.

3. Systems Development Methodologies

Methodology: A formalized approach to performing SDLC activities, techniques and deliverables. SDLC describes the broad process; a methodology defines how work is ordered, iterated and controlled.

Waterfall Development

Sequential phases with major deliverables and approval checkpoints. Benefits: clear milestones, documentation and formal control. Risks: late feedback, costly requirement changes and rework. Appropriate when needs are stable.

Agile: eXtreme Programming (XP)（極限程式設計）｜教師版 p.16

XP combines Stories, Iteration Planning, Pair Programming, Testing, Continuous Integration, Customer Approval, Acceptance Tests and Small Releases.

繁體中文完整翻譯：XP 先從使用者故事（Stories）了解需求，再估算及安排迭代計畫（Iteration Planning）。開發時可進行結對程式設計（Pair Programming），例如資深／資淺工程師或開發者／使用者協作；搭配單元測試（Unit Testing）、整合測試（Integration Testing）與持續整合（Continuous Integration），並接受顧客驗收後作小規模發布（Small Releases）。

XP｜教師版流程重點（概念重繪）
Exploration：Stories→Iteration Planning：Stories + Estimates→Iteration：Pair Programming + Development + Testing→Customer Approval / Acceptance Tests→Small Release

Testing loop：Development ↔ Testing；測試與 Collective Codebase（共同程式碼庫）及持續整合相互支援。Spikes 是為解決不確定技術問題而做的探索性方案。

Agile: SCRUM（Scrum 敏捷框架）｜教師版 p.17

Scrum organizes a ranked Product Backlog into a Sprint Backlog through Sprint Planning. A Sprint lasts 1–4 weeks, with a Daily Scrum Meeting approximately every 24 hours, followed by a Sprint Review and Sprint Retrospective.

繁體中文完整翻譯：利害關係人與顧客提出需求，由Product Owner（產品負責人）整理成有優先順序的Product Backlog（產品待辦清單）。團隊透過Sprint Planning（衝刺規劃會議）選出本輪能承諾完成的工作，形成Sprint Backlog（衝刺待辦清單）。一輪 Sprint（衝刺）為1–4 週；期間約每 24 小時開Daily Scrum（每日會議），最後展示Finished Work（完成成果）、進行Sprint Review（成果檢視）及Sprint Retrospective（流程回顧與反省）。

Scrum｜一輪 Sprint
Inputs / Product Owner→Ranked Product Backlog→Sprint Planning→Sprint Backlog→Sprint（1–4 Weeks）→Finished Work

During Sprint：Daily Scrum（每 24 小時）、Scrum Master 協助排除障礙，並可使用 Burndown / Burnup Charts 追蹤進度。

At Sprint End：Sprint Review（檢視成果）＋ Sprint Retrospective（回顧改進）。教師版圖中特別標示 Sprint 的結束日與團隊承諾的交付成果不應任意更改。

4. Object-Oriented Information Systems (OOIS)

Class: A template defining shared structure and behavior. Object: A distinct instance of a Class with Identity, State and Behavior. Attribute: Relevant information characterizing an object. Operation: Supported behavior specification. Method: Concrete implementation. Message: Request sent to an object to invoke behavior, often with parameters and return values.

Student joe = new Student();
Course sa = new Course();
joe.addCourse(sa);

Student / Course are classes; joe / sa are instances; addCourse is a method invocation or message. The Java snippet presumes suitable constructors and methods exist.

Encapsulation vs Information Hiding

Encapsulation: Combine state and operations within a Class. Information Hiding: Conceal internal representation and expose required interfaces. Encapsulation groups; information hiding restricts access.

Inheritance / Generalization / Abstraction

Generalization models an IS-A relationship. UML uses a solid line and a hollow triangle pointing to the Superclass. A Superclass is not automatically an Abstract Class. Abstract classes generally cannot be instantiated directly; concrete superclasses can.

Polymorphism, Overriding and Dynamic Binding

Polymorphism permits subtype-specific implementation through a shared parent/interface. In Java, Animal a = new Bird(); a.move(); normally executes Bird's overridden instance method; a = new Crab(); a.move(); invokes Crab's implementation. Overriding differs from Overloading. Runtime Dynamic Dispatch selects the concrete receiver's overridden method.

5. OOAD Principles and Unified Process

OOAD: Use-Case Driven, Architecture-Centric, Iterative and Incremental.

Functional View: External functions using Use Case Diagram, Activity Diagram and Use-Case Description. Structural View: Classes and static relationships using CRC Cards, Class Diagram and Object Diagram. Behavioral View: Object interactions/state using Sequence, Communication and State Machine Diagrams. All views must remain consistent.

Unified Process (UP)

UP is an iterative and incremental process using two dimensions: Phases (WHEN) and Workflows (WHAT ACTIVITIES). Its four phases are Inception (scope/business case; Lifecycle Objectives), Elaboration (core architecture/risks; Lifecycle Architecture), Construction (build/test; Initial Operational Capability) and Transition (deploy/accept; Product Release).

WorkflowInceptionElaborationConstructionTransition
Business ModelingHighMediumLowLow
RequirementsHighHighMediumLow
AnalysisMediumHighMediumLow
DesignLowHighHighLow
ImplementationLowMediumHighMedium
TestingLowMediumHighHigh
DeploymentLowLowMediumHigh

Engineering Workflows: Business Modeling, Requirements, Analysis, Design, Implementation, Test, Deployment. Supporting Workflows: Project Management, Configuration and Change Management, Environment. This intensity matrix is a qualitative learning aid, not a copied quantitative UP workload curve.

Trap: Requirements do not occur ONLY in Inception. Workflows span multiple phases. UP phases are not one-to-one renamings of four SDLC phases.

Unified Modeling Language (UML) is a standardized visual modeling language, NOT an SDLC methodology. UML diagrams can describe functional, static and behavioral views. This course teaches Use Case, Activity, Class, Object, Sequence, Communication and State Machine diagrams. Chapter 1 Introductory Seven-Step Modeling Guide

  1. Identify Business Problem, Value and Scope.
  2. Identify Stakeholders, Actors and Requirements.
  3. Build Functional View using Use Cases and activities.
  4. Derive Structural View from relevant domain concepts and responsibilities.
  5. Derive Behavioral View from object interactions and state changes.
  6. Verify syntax and validate against stakeholder needs.
  7. Iteratively refine the views and resolve inconsistencies.

Important distinction: This is an integrated Chapter 1 overview and NOT the later Chapter 4 structural CRC-to-class-diagram seven-step procedure.

Cross-Model V&V

  • Each major Use Case traces to a requirement.
  • Object lifelines correspond to meaningful Class instances.
  • Messages invoke supported responsibilities / operations.
  • Class associations support scenario interactions.
  • Alternate and exception paths are addressed.
  • Analysis models remain logical rather than cluttered with technical infrastructure.
  • Names, business rules and constraints agree across models.

Five Modeling Pitfalls

  1. Analysis confused with technical Design.
  2. Generalization hollow triangle points to subclass rather than superclass.
  3. «include» confused with «extend».
  4. Irrelevant Classes invented without requirement support.
  5. Models contradict each other because cross-model V&V is omitted.

7. End-to-End Walkthrough: Health Clinic Appointment System

English Scenario Requirements

A community health clinic currently manages appointments using telephone calls and paper schedules. Receptionists spend significant time checking physician availability, recording patient details and resolving scheduling conflicts. Patients want to request, view, reschedule and cancel appointments, while doctors need to maintain consultation availability. The clinic manager wants to prevent double bookings and reduce manual administrative workload. After an appointment has been accepted, the system should notify the patient. Sensitive patient information must not be disclosed to unauthorized users. The development team must identify the business need, define the system's functional and nonfunctional requirements, model actors and domain objects, and test whether appointment requests can be completed without scheduling conflicts. The clinic also wants to retain a staffed telephone channel for patients who cannot use the online interface. The team should select a development approach that supports early user feedback and staged delivery.

Project Initiation / System Request

FieldDerived Content

Business NeedReduce duplicate bookings, processing time and errors
RequirementsBooking, rescheduling, cancellation, availability, confirmation

Requirements Definition

  • FR-01: The system shall allow patients to request appointments.
  • FR-02: The system shall allow authorized users to reschedule appointments.
  • FR-03: The system shall allow patients to cancel appointments.
  • FR-04: The system shall allow doctors to update consultation availability.
  • FR-05: The system shall reject conflicting appointments.
  • FR-06: The system shall provide confirmation for accepted bookings.
  • NFR-01: Only authorized users may access patient information.
  • NFR-02: Booking data must be stored reliably.
  • NFR-03: The interface must be usable by patients and receptionists.

8. Cheat Sheet · Golden Rules

  1. Planning asks WHY; Analysis asks WHAT; Design asks HOW; Implementation BUILDS and DELIVERS.
  2. Every Information System should be justified by Business Value.
  3. Requirements describe capabilities; design defines technical solutions.
  4. Object is an instance of a Class; a Message requests behavior.
  5. Generalization hollow triangle always points to the Superclass.
  6. Polymorphism supports subtype-specific behavior through a common interface.
  7. OOAD is Use-Case Driven, Architecture-Centric and Iterative/Incremental.
  8. UP Phases describe WHEN; Workflows describe WHAT.

Quick Concept Check 1

In UP, the Requirements Workflow occurs only during Inception.
