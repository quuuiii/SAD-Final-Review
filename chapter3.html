1. Core Concepts & Three Functional Modeling Deliverables

Functional Modeling: The analysis activity that describes the required system functions, the actors who interact with them, and the business processes implementing each function. It is the External / Functional View of object-oriented systems analysis and design. Input: Requirements Definition. Output: Use-Case Diagram, Activity Diagrams and Use-Case Descriptions (UCDs).

2. Use-Case Diagram: Elements, Four Relationships, and Naming Rules

UML Components

ElementVisual SymbolUsage Rule
ActorStick figure / role nameExternal to the system boundary; use role names (Patient), never real names (Joe).
Use CaseEllipse / OvalInside the system boundary; name with verb + object, e.g., Register for Course.
AssociationSolid undirected communication lineConnect an Actor with a Use Case. Multiplicity may be indicated in special circumstances.
System BoundaryNamed rectangleDefine scope; actors remain outside.
«include»Dashed dependency arrow with stereotypeBase Use Case → Included Use Case (required/reusable behavior).
«extend»Dashed dependency arrow with stereotypeExtending Use Case → Base Use Case (conditional extension).
GeneralizationSolid line with hollow triangleSpecialized element → Generalized element; triangle on the general end.

Four Relationship Types from the Lecture

  1. Association: Connect Actor and Use Case; indicates communication.
  2. Include: Base use case includes another use case's functionality. Use when the included behavior is reused as a required part of the base flow in the modeled condition.
  3. Extend: Optional or conditional behavior extends the base use case. Extending use case's dashed arrow targets the base use case.
  4. Generalization: Specialized actor/use case is a subtype of a more general role/function; open triangle points to the generalized one.

3. Identifying Use Cases: Lecturer's Four-Step SOP

  1. Review the Requirements Definition. Sources can be Descriptive Requirement Statements and User Stories. Clarify the intended Actor and process/action before proceeding.
  2. Identify Primary Actors. Find who performs or initiates system business functions. Actors are roles rather than individual names.
  3. Identify Core Business Processes and Business Goals. Verbs/object phrases become candidate Use Cases.
  4. Review, Merge or Split Candidate Use Cases. Avoid microscopic use cases for every click, but also avoid oversized vague labels such as Manage Everything.

Use Cases vs User Stories

User Story emphasizes Role → Desired Capability → Value (Why). Use Case models actor interaction and system response (how the business goal unfolds). One Story may map to multiple Use Cases, and one Use Case may help realize multiple Stories. The slide includes a many-to-many instructional relation; analyze the granularity rather than assume a rigid one-to-one map.

4. Activity Diagrams: Notation and Seven Control Nodes

Activity Diagram: Depicts ordered Actions and Activities in a business process, including sequential execution, branches, parallel execution and possible object movement. Used within OOAD to model the process of a Use Case; also useful independently in BPM/BPR.

Activity vs Action and Flows

ElementDefinitionKey Rule
ActivityA coordinated behavior that may be decomposedCan be broken into subactivities
ActionA fundamental step at the current modeling levelNot further decomposed at that level
Control FlowDirected edge ordering execution of actionsIndicates execution path
Object NodeAn object/data instance used/produced during actionsRepresents a relevant object in activity flow
Object FlowDirected edge transporting object/data tokensDistinct from a pure control edge
Swimlane / PartitionGrouping nodes by responsibilityMay be vertical or horizontal
GuardBoolean condition on outgoing edgeUse [available], [unavailable] etc.

The Seven Control Nodes (slide 17)

NodeUML SymbolFunctionExam Trap
1. Initial NodeSolid filled circle ●Start of an activity executionNot the same as Activity Final.
2. Activity Final NodeBullseye ◎Terminate the entire activity executionEnds all ongoing flows in activity.
3. Flow Final NodeCircle with X ⊗Terminate only that flow/token pathDoes not terminate other active branches.
4. Decision NodeDiamond ◇Branch into alternative paths based on guardsNot a parallel Fork.
5. Merge NodeDiamond ◇Rejoin alternative (exclusive) pathsDoes not wait for simultaneous paths.
6. Fork NodeThick synchronization barSplit flow into concurrent pathsNot a conditional decision.
7. Join NodeThick synchronization barSynchronize concurrent pathsWaits for appropriate parallel tokens.

Activity Final vs Flow Final

Activity Final stops the entire process execution. Flow Final stops only one path. A rejected optional sub-flow can use Flow Final when the remainder of the overall activity should continue, while an accepted booking that completes the entire process may terminate with Activity Final. Do not use Flow Final and Activity Final interchangeably.

Decision/Merge vs Fork/Join

5. Creating Activity Diagrams: Lecturer's Five-Step SOP

  1. Set the Modeling Scope. Choose the single Use Case whose business process is being modeled; identify its entry and expected termination.
  2. Identify Actions / Activities and connect them with Flows. Name each Action with a clear verb + noun (e.g., Select Appointment Slot, Validate Booking).
  3. Identify Control Flows and Control Nodes. Add Initial, Activity Final / Flow Final, Decision / Merge and Fork / Join where required; put guards on alternatives.
  4. Identify Object Flows and Object Nodes. Show relevant business objects being passed or transformed, if they matter to the process.
  5. Draw the Activity Diagram. Use the correct UML syntax and perform a walkthrough to ensure all steps and branches are meaningful.

Step 1 source gap: The student slide leaves the exact term after “Set the modeling scope” blank. Identifying the Use Case as the scope is a context-grounded interpretation of the adjacent lecture content. The five listed step labels otherwise follow slide 21.

Activity Diagram Pitfalls

  1. Using Activity Final where only a single sub-flow must terminate.
  2. Drawing Decision/Merge instead of Fork/Join for parallel work.
  3. Failing to label conditional outgoing edges with [guards].
  4. Assigning an Action to the wrong Swimlane performer.
  5. Leaving out Object Nodes that appear in the corresponding UCD.

Two Trigger Types

External Trigger: An Actor initiates the Use Case (learner requests registration). Temporal Trigger: An event occurs at a time or schedule (automatic advertisement three days before class). Slide 22 sends students to textbook p.102 to confirm trigger naming; these are standard interpretation terms and should be checked against the specific textbook edition for grading.

Two Axes of UCD Type (slide 25)

OverviewDetail
EssentialHigh-level user/business intent without technology-specific UI stepsDetailed steps of necessary business functionality
RealHigh-level view of how the deployed system will workDetailed deployed-system steps and implementation-related interaction

Essential vs Real asks how implementation-specific the specification is. Overview vs Detail asks how much information is included. These are orthogonal dimensions; they are not four unrelated quality rankings.

Lecturer's Seven UCD Writing Guidelines (slides 29, textbook p.104–105)

  1. Write individual steps in a consistent subject–verb–object sentence form (interpretation of student-edition blank).
  2. Identify the initiator and receiver of every step clearly.
  3. Use an independent observer's perspective rather than subjective narration.
  4. Stay at a consistent level of abstraction.
  5. Use a sensible number of steps to cover the meaningful process.
  6. Apply the KISS principle (Keep It Simple and Straightforward; common interpretation, lecturer slide leaves this term blank) when organizing flows.
  7. Explicitly document loop conditions and termination.

Transparency: Guidelines 1 and 6 contain unfilled blanks in the supplied student slides. The expanded SVO and KISS labels are teaching interpretations, not verified verbatim answers from the instructor's filled-in key.

8. V&V: Formal Walkthrough and Eight Cross-Model Rules

Verification: Check artifacts for correct and internally consistent UML syntax, flow and fields. Validation: Confirm the functional models satisfy business needs with the Client.

Formal Walkthrough Roles (slide 30)

RoleResponsibility
Facilitator / Host (e.g., PM)Arrange meeting and lead review process
PresenterAuthor presents Use Cases, Activity Diagrams and UCDs
Recorder / ScribeDocument defects, questions and corrections
Client / StakeholderConfirm that the modeled functions support real business operations

The Eight Lecturer Rules (slides 31–32)

  1. Action-to-event coverage: Every Action / Activity on an Activity Diagram must have at least one corresponding event in its UCD.
  2. Object-node coverage: Every Object Node in an Activity Diagram must be mentioned in a UCD event.
  3. Order consistency: The sequence of UCD events must match the activity-flow order.
  4. One-to-one documentation: Each Use Case has one and only one UCD.
  5. Actor consistency: All Actors listed in a UCD must appear in the Use-Case Diagram (student slide contains a blank; Actor is the course-context interpretation).
  6. Stakeholder review: Stakeholders in the UCD should preferably appear in the diagram if they are true interacting Actor roles; evaluate whether an interested but non-interacting stakeholder truly belongs there.
  7. Relationship consistency: Every relationship specified in the UCD must be represented on the Use-Case Diagram.
  8. Diagram syntax: Enforce all diagram-specific element, label, arrow and control-node rules.

Typical Point-Deduction Errors

  1. Wrong include / extend arrow direction or dashed stereotype.
  2. Actor represented as a specific real person's name instead of a role.
  3. UCD event ordering contradicts the Activity Diagram.
  4. Flow Final used to end an entire activity, or Activity Final ends all parallel tasks unexpectedly.
  5. Missing UCD for a diagrammed Use Case, or missing Actors/relationships in one artifact.

9. End-to-End Case: Doctor–Patient Appointment System

A Patient should be able to search for available consultation periods, request an appointment, view existing appointments, and cancel or reschedule a visit. The system must check the requested period before recording a new booking, reject conflicting time slots, and notify the requester of an accepted appointment. Patient information must remain available only to authorized users. The clinic wants to preserve its staffed reception desk because some patients cannot use an online interface. Analysts must derive use cases from these requirements, construct an Activity Diagram for the booking process, write a detailed Use-Case Description, and perform a walkthrough to verify that both successful and unavailable-slot scenarios are consistently represented across all functional models.

11. Cheat Sheet, Golden Rules & High-Discrimination Quiz

Eight Golden Rules

  1. Functional Modeling has THREE artifacts: Use-Case Diagram → Activity Diagram → UCD.
  2. Use Cases originate from business processes/goals; Actors are ROLES, never personal names.
  3. «include» arrow: Base → Included; «extend» arrow: Extension → Base.
  4. Generalization hollow triangle always points to the GENERAL element.
  5. Decision/Merge handles alternatives; Fork/Join handles concurrency.
  6. Activity Final stops the whole activity; Flow Final stops only one path.
  7. One Use Case has exactly one UCD, with normal, sub-, alternative and exception flows.
  8. Each Activity Action/Object Node, Actor and Relationship must be consistent with its UCD and Use-Case Diagram.
