1. Behavioral Modeling: Scope, Objectives and Artifact Relationships

Behavioral Modeling: Dynamic modeling of how interacting objects collaborate to fulfill use cases and how an important business object changes state during its lifetime. The two main model families are Interaction Diagrams and Behavioral State Machines. The lecturer explicitly states Behavioral Modeling is iterative and can induce changes to functional and structural models (2026 lecture pp.4–8).

中文：Functional Model 說明「使用者需要系統做什麼」，Structural Model 說明「有哪些物件及責任」，Behavioral Model 說明「物件以什麼訊息及順序合作」以及「重要物件何時轉換狀態」。它不是用來重新描寫靜態 Class 清單，也不是重新畫一次 Use Case。

2. Interaction Diagrams: Sequence vs Communication and Message Types

The 2026 slides identify two UML interaction diagrams: (1) Sequence Diagram, emphasizing timing/order, and (2) Communication Diagram, emphasizing the pattern of message flow between linked objects. Slide 7 explicitly says Communication Diagrams are not included in the assigned textbook; the comparison and illustrative notation below derive from the lecture plus standard UML explanation, not from missing textbook pages.

Message Fundamentals

Slide 6 uses a Java-style Student–Course example: Student.registerCourse(Course c) invokes c.add(stu_ID), then obtains a returned boolean. In this interaction, Student sends a Call Message and Course provides a Return Message. The sender's Class need not implement the receiver's operation: the receiver owns its behavior.

public class Student {
  private String stu_ID;
  public String registerCourse(Course c) {
    boolean accepted = c.add(stu_ID);
    return accepted ? "accepted" : "rejected";
  }
}

Execution vs Return

An Execution Occurrence is not the same as a Lifeline. The Lifeline persists as the participant exists, while the Execution Occurrence marks active execution. Returning a value is different from sending another business request. The lecture's example on slides 10–11 uses the execution bar specifically for this distinction.

5. Official Borrow Books Example: Sequence Diagram Drives Class Refinement

Lecture pp.23–32 walks from the Library Book Collection Management System and the Borrow Books UCD through candidate classes, a UC-level Class Diagram, Sequence Diagram, discussion of new business information and a revised Class Diagram. This is particularly important: behavioral modeling can reveal structural gaps.

Derivation

  1. Identify the Borrow Books Normal Flow: a borrower requests a book, the system checks required conditions, records checkout, and responds.
  2. Inspect Candidate Classes: Student, Librarian, Book, Book Collection and other concepts shown in the case; determine which are domain entities, actors, boundaries or controls.
  3. Prepare UC-Level Class Diagram: confirm classes' responsibilities and associations before building the Sequence Diagram.
  4. Build Sequence Diagram: allocate each UCD event to interacting instances.
  5. Ask Design Questions: who is the user of the future online system, which object becomes an interface, and where is checkout information stored?
  6. Revise Class Diagram: introduce or revise a checkout transaction representation where the scenario requires it; reflect corresponding operations and associations.

6. CRUDE Analysis: Five Operations and System-Wide Collaboration Matrix

CRUDE = Create, Read, Update, Delete, Execute. Slide 33 explicitly defines these five labels and says a Matrix helps identify or verify object collaborations. Its strength is a system-wide interaction overview, complementing scenario-specific Sequence Diagrams.

How to read a matrix: Row = initiating actor/class; Column = target class; entry = permitted/required interaction. A blank indicates no modeled collaboration in this scope, not necessarily that the class can never participate in another Use Case.

Procedure

  1. Collect the relevant actors/classes from Use Cases and UC-level CD.
  2. Review Sequence Diagram messages and responsibilities.
  3. Identify which targets each initiator Creates, Reads, Updates, Deletes or Executes.
  4. Populate the matrix with C / R / U / D / E, using multiple labels where appropriate.
  5. Find unexpected blanks, unsupported associations or classes without meaningful collaboration.
  6. Revisit Functional, Structural and Behavioral Models as needed.

Official cases: Slide 34 uses Campus Housing System with Apartment Owner, Student, Staff and Apartment. Slide 35 uses the Library Book Collection Management System for a system-wide CRUDE Matrix and asks which classes appear to have no collaboration. The student image is partially not text-extractable, so the Parcel matrix here is an explicitly illustrative replacement rather than claimed exact numerical/transcription content.

Exam trap: A class with no links in a particular matrix is a candidate for investigation, not automatic deletion. Determine whether another UC requires the class.

7. Behavioral State Machines: Syntax, State/Events/Guard and Black Holes

Behavioral State Machine: A dynamic model of the state changes of a focal object in response to events throughout its lifecycle. The diagram models one important business object's states, not the order of all participants' messages. Focus on Classes with meaningful status-dependent behavior (slides 36–38).

Black Hole and Dead-End States

Lecture p.40 asks which state creates a Black Hole in a car-rental membership machine. The phrase describes a state into which the model can transition but from which no valid outgoing transition can be taken under the stated rules when one should exist. This may indicate missing events, misunderstood lifecycle conditions or an intentionally terminal state. Distinguish an erroneous black hole from a correctly modeled Final State.

8. State Machine Construction: Five-Step SOP + Lecturer's Car-Rental Case

Official five-step SOP, slide 41:

  1. Set the Context: Prepare relevant artifacts and select one Class from Class Diagram whose lifecycle requires modeling. The student slide leaves the exact preparatory artifact in a blank; use the validated Functional/Structural material as evidence.
  2. Identify States: Include Initial State, meaningful Stable States and appropriate Final State(s).
  3. Lay Out the Diagram: Prefer readable left-to-right and top-down lifecycle order.
  4. Add Transitions: Identify triggering Events, executed Actions and Guards.
  5. Validate the Model: Ensure required states are reachable and important business transitions are covered.

Official Car-Rental Membership Exercise (slide 40)

Scenario: Customers deposit NT$10,000 to become Regular Members. On the second rental a Regular Member becomes Silver. After five rentals a Silver Member becomes Gold. Gold returns to Silver after six months without rentals. A member who damages a car becomes Frozen, cannot rent for six months and then returns to Regular. A Regular Member without any rentals for over three years loses membership and must apply again.

Finding a Potential Black Hole

After checking the model, ask whether each nonterminal state has at least one reachable future transition. The state Expired can be intentionally terminal for the current Membership object, but the business says a customer can reapply for a new membership; this may be represented by a new object rather than reactivating the old one. If one incorrectly draws Expired as a stable state with no path to a new registration despite requiring the same object to be reused, it becomes a modeling ambiguity. Whether a state's lack of outgoing arrows is an error depends on the chosen lifecycle scope.

9. Full Clinic Walkthrough: Requirements → CRC/Class → Sequence → State → CRUDE

English Scenario Requirements (Original, approximately 150 words)

A community clinic requires an appointment system for patients who wish to schedule consultations with doctors. A Patient can select an available Doctor and Consultation Slot, submit a booking request, and receive either a confirmation or a rejection. Receptionists may assist patients who cannot access the online service. The System must validate availability before confirming any request, prevent overlapping bookings for the same Doctor, and record each accepted Appointment with its identifier, patient, doctor, scheduled time and status. Patients may cancel or reschedule under approved clinic policies. Doctors can maintain available consultation times. The clinic manager expects reduced duplication and accurate schedules. Analysts have completed functional and structural models and must now identify the objects exchanging messages, model the normal booking scenario, inspect how an Appointment's state changes, and verify that Class responsibilities, message directions, status attributes and system requirements are consistent across all models.

11. V&V: Sequence–Class–State–Functional Consistency and Pitfalls

Lecture p.42 assigns students to read textbook p.182 for Behavioral V&V and Functional–Behavioral cross-check, and p.183 for Structural–Behavioral cross-check. The corresponding textbook Behavioral chapter PDF is not among the currently uploaded five textbook PDFs. Consequently the rules below are source-aligned teaching checks synthesized from the slides, not falsely quoted from unavailable textbook pages.

Scenario and Diagram Walkthrough SOP

  1. Select a UCD scenario and record its trigger, normal/alternate steps and result.
  2. Verify an Actor and each relevant Class participant appear in the Sequence Diagram.
  3. For each UCD action, identify sender, receiver, method and meaningful parameter; check event order.
  4. Ensure every receiver operation and relevant association can be found in the UC-level Class Diagram, or revise the Structural Model.
  5. Check State Machine Events correspond to operations/events that actually occur in use cases and Sequence Diagrams.
  6. Check state names map to meaningful object attributes; Guards match business rules.
  7. Use CRUDE to compare class collaborations across several Use Cases and discover unsupported/orphan Classes.
  8. Walk through exceptions, unreachable states, termination paths, and revise Functional, Structural and Behavioral Models bidirectionally.

Five Common Modeling Mistakes

  1. Confusing one Instance Sequence Scenario with a Generic Diagram containing all alternate paths.
  2. Reversing message direction or giving an operation to the wrong receiving Class.
  3. Treating a return dashed arrow as a second method invocation.
  4. Using Activity Diagram steps as State names, instead of modeling the focal object's attributes/lifecycle.
  5. Ignoring unreachable/black-hole states or forgetting to update Class attributes when state transitions imply new status information.

12. Cheat Sheet, Golden Rules, Concept Traps and Mastery

Eight 1-Sentence Golden Rules

  1. Behavioral Models show how object collaborations realize Use Cases and how focal objects change states.
  2. In Sequence Diagrams, time proceeds top-to-bottom and the receiving object owns the called operation.
  3. For this course, create Instance Sequence Diagrams based on one specific UCD scenario.
  4. Sequence Diagram SOP = Context → Participants → Lifelines → Messages → Execution Occurrences → Validation.
  5. CRUDE stands for Create, Read, Update, Delete and Execute, and provides a system-wide collaboration check.
  6. A State Machine models the lifecycle of one object, while an Activity Diagram models workflow actions.
  7. A Transition is triggered by an Event, may depend on a [Guard], and may perform an Action.
  8. Behavioral V&V is bidirectional: Messages and State Transitions can require revisions to the Class Diagram and Functional Models.
