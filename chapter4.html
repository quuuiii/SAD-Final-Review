1. Structural Modeling: Purpose, Scope and Three Representations

Structural Modeling: A process of representing real-world objects involved in business processes as classes, defining their structural content, and establishing relationships among the classes. It provides the Static / Structural View of OOAD, supporting the Functional View.

中文：分析活動流程中的 people, places, things、交易與事件，再思考它們承載的資料、應負責的行為，以及彼此的關係。Class Diagram 是靜態模型，不直接表示使用案例執行時的先後順序。

2. Class Identification: From UCD Events to Domain Classes

Grounded lecture process (pp. 11–12)

  1. Focus on a selected Use Case. Identify relevant business objects: people, places, things, transactions/events, roles.
  2. Inspect the UCD event-flow statements. Nouns and noun phrases suggest candidate Classes or Attributes. Verbs and verb phrases suggest candidate Operations or collaborations.
  3. Examine domain meaning and scope. Some nouns refer to values, concepts or actions, and not every highlighted candidate survives as a Class.
  4. Check the requirement boundary. Only include objects that the information system actually needs to represent, not everything in the real world.

Slide 12 explicitly cautions that not every red-box candidate becomes a Class after analysis.

3. CRC Cards: Class, Knowing/Doing Responsibilities and Collaboration

CRC stands for Class–Responsibility–Collaboration. Each card states a Class's responsibilities and the other Classes needed to realize those responsibilities for a particular Use Case.

Knowing vs Doing

ResponsibilityDefinitionTypical translation to Class Diagram
KnowingInformation that instances know or provideCandidate Attributes and Query Operations
DoingActivities an object performs for other objects or for itselfCandidate Operations / Methods
CollaborationRequesting services from another classPossible Associations and Messages

Client vs Server responsibility

class A {
  public void ma(B b) {
    b.mb();
  }
}
class B {
  public void mb() { /* behavior */ }
}

In the illustrated call b.mb(), A is the requestor/client and B is the responder/collaborator/server. The object receiving the requested message should own the corresponding responsibility.

CRC Role-Playing (slide 19)

  1. Pick a Use Case / Scenario.
  2. Assign team members to represent the objects/classes in that case.
  3. Walk through the use case's event flows carefully, identifying minimal responsibilities and negotiating collaboration requests.
  4. Construct/update CRC cards to reflect the least sufficient set of responsibilities and collaborators.

From Class Diagram to Coding (slide 37)

Associations in the CD may become reference attributes in a receiver Class definition.

public class Employee {
    private Boss boss;

    public Employee(Boss boss) {
        this.boss = boss;
    }
}

Given a Boss–Employee association of one Boss managing one or more Employees, each Employee may store a reference to the corresponding Boss object. Exact field ownership and navigability must be consistent with the model and implementation design; UML associations do not always require one specific code representation.

8. Verification, Validation & Functional–Structural Balance

The 2026 slides at pp. 40–41 instruct analysts to walkthrough the structural model with developers/users, explain the rationale for each Class, and consult textbook p.152 for V&V rules and p.154 for balancing Functional and Structural Models. The student slide does not reproduce those rule lists, so the checklist below is a transparent teaching synthesis, NOT a verbatim transcription of those textbook pages.

Structural Walkthrough

  1. Start from the selected Use Case and read Normal and Alternate UCD event flows.
  2. For each scenario, identify the active objects and confirm required classes exist.
  3. Check CRC cards: Knowing duties should have Attributes; Doing duties should have Operations.
  4. Check collaborators: Class Diagram Associations should support required calls.
  5. Validate multiplicity at both endpoints using concrete object examples.
  6. Use Object Diagrams for sample objects, values and links; revise missing/redundant classes.
  7. Remove gold-plating and unsupported attributes or associations.
  8. Confirm the model with stakeholder/developer walkthrough and revise it iteratively.

Five Frequent Exam Pitfalls

  1. Drawing simplified format in exams: Slide 22 explicitly requires Standard Class Diagram format unless simplified is requested.
  2. Multiplicity on wrong end: Always interpret the number at the opposite association endpoint.
  3. Inventing Associations: A real-world relationship is not enough; it must serve System Scope and Requirements.
  4. Composition vs Aggregation: Filled and hollow diamonds express different ownership/lifecycle semantics.
  5. Skipping CRC Role-Playing: Drawing classes directly without testing responsibilities against UCD event flows can leave missing operations and collaborations.

9. End-to-End Case Study: Doctor–Patient Appointment System

Scenario Requirements (Original English, about 150 words)

A neighborhood health clinic needs an appointment system to replace fragmented paper schedules and staff phone logs. Patients should request appointments by selecting a doctor and consultation period. Receptionists may book on a patient's behalf, and doctors maintain the periods available for consultation. Before an appointment is confirmed, the system must check physician availability and prevent conflicts. Each accepted appointment should record the patient, physician, scheduled period, status, and a unique appointment identifier. Patients should be able to cancel or reschedule under the clinic's approved rules. The clinic manager wants accurate daily schedules and fewer duplicate bookings. Sensitive patient information must remain protected from unauthorized access. The analyst must identify relevant domain classes, assign their knowing and doing responsibilities using CRC cards, derive a complete Class Diagram, instantiate sample objects, and verify that the structural model supports successful and rejected booking scenarios without including irrelevant objects outside the agreed system scope.

Step 3: CRC Role-Play

  1. Patient submits desired doctor and time to BookingUI.
  2. BookingUI requests BookingController to schedule an Appointment.

11. Golden Rules, Quick Exam Checks and Mastery

Eight 1-Sentence Golden Rules

  1. Structural Modeling represents Classes, their structural contents and relationships.
  2. CRC = Class + Knowing/Doing Responsibilities + Collaborators.
  3. Read UCD nouns for candidate Classes and verbs for candidate Operations, but filter by scope.
  4. Generalization IS-A uses a hollow triangle pointing to the Superclass.
  5. Aggregation uses a hollow diamond; Composition uses a filled diamond at the Whole end.
  6. Read Multiplicity at the opposite association endpoint and label directional relationships.
  7. Always use the Standard Class Diagram format in exams unless Simplified is requested.
  8. 7-Step CRC-to-Class-Diagram creation ends with review and validation; Object Diagrams can trigger revisions.
