# Ch3 · Functional Modeling

> **Lecture basis:** 2026 Ch03（Use-Case Diagram、Activity Diagram、Use-Case Description）；113 Final Q9、Q11、Q29、Q32。

## Core Definition

- **Functional Model**：說明業務流程、參與角色與系統功能。
- **Actor**：在系統邊界外與 Use Case 互動的角色，而非具體人名。
- **Use Case**：角色和系統合作達成的明確業務目標。
- **Use-Case Description (UCD)**：以文字寫出 Trigger、Preconditions、Main Flow、Alternates、Postconditions。
- **Activity Diagram**：展現行為、分支、並行與控制流程。

## Key Elements · Three Modeling Artifacts

| Artifact | Key question | Main use |
|---|---|---|
| **Use-Case Diagram** | Who and what? | Actor、Use Case、System Boundary |
| **Activity Diagram** | Which steps and decisions? | Action、Decision / Merge、Fork / Join、Swimlane |
| **Use-Case Description** | What occurs in a scenario? | Main、Alternate、Exception Flow |

## Why & How · Four Relationships

| Relationship | When to use | UML direction |
|---|---|---|
| **Association** | Actor 參與 Use Case | 一般實線 |
| **«include»** | 必須執行且可重用的共同行為 | Base → Included |
| **«extend»** | 有條件時才補充的行為 | Extension → Base |
| **Generalization** | 特化角色或用例承接共通互動 | 空心三角朝一般者 |

**Actor Generalization:** 若 GraduateStudent 是 Student 的一種，且具備全部共同互動並增加特殊操作，可以讓 GraduateStudent 繼承 Student Actor 的關聯。

**«include» vs «extend»:** Enroll Course 每次都要 Check Prerequisites，可採 include；課程額滿時才允許 Join Waiting List，可採 extend。判斷分水嶺是**必要性**與**條件式擴充**，不是箭頭長得像不像。

## User Story vs Use Case

- **User Story**：說明角色需要的 **Why / Value**，例如「我要快速選課，避免錯過名額」。
- **Use Case**：展開角色與系統的 **Interaction Flow**，例如 Search Courses、Enroll Course、Drop Course。
- **Why 1:N is possible:** 一個 Story 可能涉及多個獨立業務目標，因而拆為多個 Use Cases。
- **Important caution:** **1:N 不是 UML 固定強制規則**，也可能 1:1 或由多個 Stories 共同補足一個 Use Case。
- **How ≠ Code:** UCD 的「如何完成」指互動步驟，不是 Java 或 SQL 實作。

## Concrete Example · Online Course Registration

| Event | Actor | Model result |
|---|---|---|
| 查詢課程 | **Student** | Search Course |
| 送出加選 | **Student** | Enroll Course，包含資格檢查 |
| 名額已滿 | **Student** | 依政策選擇候補的 Alternate Flow |
| 修改課程名額 | **Administrator** | Maintain Course Capacity |

**Cross-model consistency:** UCD 中的「確認學生資格」應在 Activity Diagram 有對應步驟，並在 Class Diagram 找得到可承擔責任的 Operation。

## Essential UCD vs Real UCD

| Aspect | **Essential UCD** | **Real UCD** |
|---|---|---|
| Focus | 業務意圖、系統責任 | 具體使用者操作及畫面 |
| UI dependence | 不依賴介面技術 | 記錄表單、按鈕及提示 |
| Example | Student requests enrollment | Student selects a course and clicks Enroll |

**Why:** 先確認功能是否合理，再決定介面細節，避免讓既有畫面綁架需求。

## Exam Traps & Checkpoints

- **Trap:** Actor 不是角色真名；角色可由人員、其他系統等擔任。
- **Trap:** «include» 和 «extend» 不能只靠箭頭方向辨識，必須先讀條件。
- **Q9 / Q11:** Activity / UCD Events 應與 Class Operations 保持模型一致。
- **Q29 / Q32:** Real UCD 可用於 UI Navigation 設計；不能與 Essential UCD 混淆。

**Source boundary:** 教授投影片提供 UML 模型與範例；User Story 對應方式為額外的教學對照。
