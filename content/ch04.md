# Ch4 · Structural Modeling & Class Design

> **Lecture basis:** 2026 Ch04 Structural Modeling pp.5–11、23–37；Ch05 p.28 手寫 ArrayList；113 Final Q12、Q15–16、Q21、Q23、Q37。

## Core Definition

- **Structural Modeling**：從實際業務的 **People、Places、Things** 辨識 Classes，並建立它們的 Attributes、Operations 與 Relationships。
- **Class**：具有共通性質與行為的 Object 模板。
- **Object / Instance**：某個具體個體，例如學生 S001。
- **CRC Card**：以 **Class、Responsibilities、Collaborators** 推導責任分工。
- **Class Diagram**：呈現類別的靜態結構與 Multiplicity。

## Key Elements · People, Places, Things

| Category | Real-world example | Candidate class |
|---|---|---|
| **People** | 學生、客戶、館員 | Student、Customer、Librarian |
| **Places** | 教室、圖書館、旅館房間 | Classroom、Library、Room |
| **Things** | 課程、書籍、借閱紀錄 | Course、Book、Checkout |

**Why:** UCD 中的主詞、受詞及事件能提供候選 Class，但不是每個名詞都該變成一個 Class；必須檢查它是否需要獨立身分、資料與行為。

### Three Compartments in a Class

| Compartment | Example | Purpose |
|---|---|---|
| **Class Name** | Student | 類別名稱 |
| **Attributes** | studentId: String | 物件所持有的資料 |
| **Operations** | enroll(courseId) | 物件可執行的行為 |

## Why & How · UML Relationships

| Type | Decision question | Example |
|---|---|---|
| **Generalization** | Is-a? | GraduateStudent → Student |
| **Association** | 有一般業務互動嗎？ | Student enrolls Course |
| **Aggregation** | 是 Whole–Part，但部分可獨立嗎？ | Department — Teacher，視模型而定 |
| **Composition** | Part 生命週期依附 Whole 嗎？ | Order — OrderLine，視規則而定 |
| **Multiplicity** | 一端最多／最少幾個實例？ | 1、0..1、0..*、1..* |

**Common trap:** 「John is a Student」是 Instance-of，不是 Generalization。「Customer buys Product」通常是 Association，不是 Composition。

## Inheritance · No Duplicate Declaration

**Superclass = Student** 已定義 addCourse() 或 payTuition() 時，**Subclass = GradStudent** 可以直接使用 inherited methods。這是將共通責任集中管理，**無須重新宣告**；只有計費規則或其他行為確實不同時，才考慮 **Method Overriding**。

## Association → Implementation: ArrayList

**Ch05 p.28 handwritten answer:** **Book class may contain an ArrayList to store all check-out records.**

**Design reasoning**

- **Association** 表達物件之間的業務關聯。
- **Multiplicity** 決定是單一 reference 還是多筆 collection。
- **Checkout Record** 需要 checkoutDate、returnDate 等欄位，適合建立 Checkout 類別。
- **ArrayList of Checkout** 可表達一冊書包含多筆借閱歷史的實作選擇。
- **Persistence**：正式系統也可能把紀錄存於 Database / Repository；**不是所有關聯都必須實作為 ArrayList**。

**Concrete Example:** Book 與 Checkout 的關聯在分析圖呈現為多筆借閱紀錄；到了 Design Model 才選擇 Collection、Reference 或資料表。Sequence Diagram 若發現缺少歷史紀錄責任，應回頭修正 Class Diagram。

## Cohesion, Coupling & Connascence

| Term | Meaning | Design goal |
|---|---|---|
| **Cohesion** | 模組內部責任的相關程度 | High Cohesion |
| **Coupling** | 不同模組彼此依賴程度 | Low Coupling |
| **Connascence** | 程式元素必須共同變更或遵守同一約定的相依現象 | 降低不必要的跨模組共同變更 |

### Connascence · Three Levels in 113 Exam Q37

| Exam Level | Handwritten explanation | Example |
|---|---|---|
| **Level 0 · Code** | 重複程式碼散落各處 | 多處複製列印迴圈 |
| **Level 1 · Method** | 共通行為抽取成方法 | printReport() |
| **Level 2 · Class** | 相關方法與狀態歸類於 Class | ReportPrinter |

**Source caution:** 這是 113 考古題手寫使用的三層分類，不能聲稱是所有 Connascence 文獻共同採用的唯一正式分級。

## Exam Traps & Checkpoints

- **Q15:** 抽取共通 Superclass 是 **Factoring**。
- **Q16 / Q21:** 內聚 **Cohesion** 看模組內；耦合 **Coupling** 看模組間。Q21 的手寫判斷與一般定義之間有歧義，不宜照單全收。
- **Q23:** **Precondition** 發生在方法前、**Postcondition** 是執行後保證、**Invariant** 是維持有效狀態的約束。
- **Trap:** Association 本身不等於 ArrayList；先看 Multiplicity。
