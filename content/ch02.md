# Ch2 · Requirements Determination

> **Lecture basis:** 2026 Ch02 pp.3–42（含老師手寫與 System Proposal p.42）；113 Final Q13。

## Core Definition

- **Requirement**：系統須提供的能力或遵守的條件。
- **Functional Requirement**：系統要做什麼，例如 Search Course、Enroll Course。
- **Non-functional Requirement**：系統執行時須符合的品質、限制與環境條件。
- **Requirements Determination**：蒐集、分析、確認與記錄需求的迭代過程。

## Key Elements · Requirements Types

| Type | Meaning | Course Registration example |
|---|---|---|
| **Functional** | 業務功能 | 學生可搜尋並加退選課程 |
| **Operational** | 運作環境 | 支援校方登入服務 |
| **Performance** | 速度與負載 | 指定回應時間及同時使用人數 |
| **Security** | 授權與資料保護 | 只有本人能修改自己的選課 |
| **Political & Cultural** | 組織政策限制 | 遵循學分及選課規則 |

## Why & How · Discover the Actual Business Problem

| Strategy | Ask this question |
|---|---|
| **Problem Analysis** | 使用者正在遇到什麼痛點？ |
| **Root Cause Analysis** | 真正造成問題的原因是什麼？可用 Fishbone Diagram。 |
| **Duration Analysis** | 哪個步驟最耗時？能否減少或並行？ |
| **Activity-Based Costing (ABC)** | 成本由哪些活動產生？ |
| **Informal Benchmarking** | 其他組織如何處理？ |
| **Outcome Analysis** | 從理想結果倒推流程，應怎麼改？ |
| **Technology Analysis** | 哪些新技術讓新作法變得可行？ |
| **Activity Elimination** | 哪個步驟可以完全移除？ |

### Five Gathering Techniques

- **Interviews**：深入理解使用者動機與例外情況。
- **Questionnaires**：收集大量標準化回饋。
- **Observation**：核對實際作業；注意 Hawthorne Effect。
- **Document Analysis**：分析既有表單、紀錄與政策。
- **Joint Application Development (JAD)**：由相關角色共同討論並確認需求。

## VT4C · Requirements Quality

| Principle | Problem | How to improve |
|---|---|---|
| **Clear** | 用語有歧義 | 明確寫出 Actor、Action、Object |
| **Verifiable** | 無法測量是否達成 | 加上驗收標準、條件與數字 |
| **Consistent** | 不同需求互相矛盾 | 訂出一致規則及例外 |
| **Complete** | 漏掉情境與輸出 | 加入 Main / Alternate / Exception Cases |
| **Concise** | 贅字或功能鍍金 | 刪除重複、拆分需求 |
| **Traceable** | 無法追來源與測試 | Requirement ID → Use Case → Test Case |

**Concrete Example**

- **Before:**「選課網站要快、好用且安全。」
- **After:**「200 人同時查課時，95% 的請求在 2 秒內回應；學生須登入才能送出加退選。」
- **Why:** Performance 與 Security 可以獨立驗證。時間門檻為示例，不是課堂指定數字。

## System Proposal · What Belongs in It?

**System Proposal** 集合 Planning 與 Analysis 期間形成的資料，方便主管做投資及推進決策。

| Section in Ch02 p.42 | Core purpose |
|---|---|
| **Executive Summary** | 摘要所有關鍵資訊，讓主管判斷應詳細閱讀哪些章節 |
| **System Request** | Business Need、Sponsor、Business Value |
| **Workplan** | 時程、工作與資源 |
| **Feasibility Analysis** | Technical、Economic、Organizational Feasibility |
| **Requirements Definition** | Functional / Non-functional Requirements |
| **To-Be Models** | Functional、Structural、Behavioral Models |

**Executive Summary:** 文件呈現時放前面；**實務上建議最後撰寫**，才能準確濃縮分析結果。投影片 p.42 明確記載的是其摘要用途，沒有將寫作先後列為硬性規定。較完整書面提案另可含 Table of Contents、Appendices，須與投影片六項列點區分。

## Exam Traps & Checkpoints

- **Q13:** Analysis Model 聚焦功能需求；Design 仍須處理 Non-functional Requirements。
- **Trap:** Fishbone Diagram 的 Root Cause 不等同表面的 Business Problem。
- **Trap:** **Clear ≠ Verifiable**；一句話容易理解，不代表能客觀驗收。
