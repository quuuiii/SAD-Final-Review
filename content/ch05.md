# Ch5 · Behavioral Modeling

> **Lecture basis:** 2026 Ch05 Behavioral Modeling pp.5–10、19–32；Ch04 類別分類；113 Final Q9、Q11、Q17–18。

## Core Definition

- **Behavioral Modeling**：描述 Objects 如何互動完成 Use Cases，以及重要業務物件如何隨事件轉換狀態。
- **Sequence Diagram**：按時間先後呈現 Actor / Object 之間的 Messages。
- **Communication Diagram**：強調 Objects 的連結及訊息交換。
- **State Machine Diagram**：以 State、Event、Guard、Transition 描述物件生命週期。
- **CRUDE Matrix**：以 Create、Read、Update、Delete、Execute 檢查用例和資料操作責任。

## Sequence Diagram · Key Elements

| Element | Purpose |
|---|---|
| **Actor** | 系統邊界外的角色 |
| **Lifeline** | Actor / Object 隨時間存在的線 |
| **Message** | 呼叫接收者的 Operation，可帶 Parameters |
| **Return** | 回傳結果 |
| **Activation** | 接收者正在執行方法 |
| **Main Event Flow** | 課堂以主要正常情境建立 Instance Sequence Diagram |

**Why:** 每個 Message 的 Receiver 應找得到相對應的 Operation；否則 Sequence Diagram 與 Class Diagram 不一致，必須回頭修正模型。

## Concrete Example · Library Checkout

### As-Is: At the Library Counter

1. **Student** 向 **Librarian** 提出借閱。
2. **Librarian** 操作系統，檢查資格、罰款和館藏。
3. 系統處理借閱後由館員告知結果。

### To-Be: Online Self-Service

1. **Student** 成為直接操作線上系統的主要 **Actor**。
2. **BorrowBookUI / Boundary Class** 接收搜尋與借閱請求。
3. **CheckoutController / Control Class** 協調驗證、罰款與借閱規則。
4. **Book / Student / Checkout / Entity Classes** 儲存業務資料。
5. **UI** 顯示成功、失敗及可採取的下一步。

**Why & How:** 線下館員負責的輸入、溝通與回覆，線上由 **Interface / Boundary Class** 接手。**Control Class** 負責流程協調，**Entity Class** 負責資料與狀態。Librarian 是否仍是次要 Actor，取決於是否有人工審核的用例。

**Sequence Sketch:** Student → BorrowBookUI → CheckoutController → Book / Checkout → BorrowBookUI。

## Sequence → Class Diagram Revision

- **Checkout** 需要 checkoutDate、returnDate 與相關學生、書籍的參照。
- **Ch05 p.28 handwritten:** Book 可透過 **ArrayList** 保存多筆 Check-out Records。
- **Why:** 循序圖讓我們發現需要儲存的物件責任；如果 Class Diagram 沒有 Checkout，應重新評估候選 Class 與 Relationships。
- **Design alternative:** 長期多使用者系統也可能將紀錄交由 Repository / Database 管理。

## State Machine vs Activity

| Term | What it means | Example |
|---|---|---|
| **State** | 物件持續的業務條件 | Available / CheckedOut |
| **Event** | 觸發變化的事件 | ReturnBook |
| **Guard** | 控制能否轉換的條件 | noOutstandingFine |
| **Transition** | State A → State B | CheckedOut → Available |
| **Activity / Action** | 某個活動或瞬間執行的步驟 | Click Submit |

**Why:** Click Submit 是 UI Action，不是 Book 的業務 State。狀態可能來自多個屬性，不應僵化理解為「必須僅對應一個欄位」。

## Exam Traps & Checkpoints

- **Q9 / Q11:** CRUDE、UCD Events、Activity Actions、Class Operations 應保持跨模型一致。
- **Q17:** 原卷強調 States 與 Object Attributes 的關係；狀態可由多個條件共同決定。
- **Q18:** CRUDE 中的資料操作應能對應 Structural Model 的 Classes。
- **Trap:** **Sequence** 重訊息的時間順序；**Communication** 重連結與訊息關係。
- **Trap:** UI 操作步驟不一定是業務物件的 State。
